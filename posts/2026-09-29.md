**核心概念（簡單說）：**
這是回應前一則「現在沒辦法直接給別人看你的 prompt」的自嘲式補刀：當有人追問「你的神 prompt 是什麼」，答案往往平凡得驚人。真正讓結果變好的，是 agent 背後已經累積的脈絡——skills、參考 repo、專案記憶、工具——而不是那一句話本身。

換句話說，prompt 已經從「咒語」退化成「開關」，真正的功力在於你事先幫 agent 準備好的環境。

**前端工程師實際應用：**
- **跟你工作的關聯：** 與其花時間收藏別人的「萬用 prompt」，不如投資在自己專案的 `CLAUDE.md`、skills 與範例檔，讓一句簡單指令就能產出高品質結果。
- **具體場景：** 遇到複雜的狀態管理問題（例如 Zustand store 與 React Query cache 互相覆寫），直接說「幫我一步一步想清楚這個問題」，讓 Claude 先列出資料流與假設，再決定要不要動手改 code。
- **這週可以嘗試：** 下次卡關時先不要寫長 prompt，只說這句話並觀察 Claude 的推理步驟，再比較它和你精心撰寫的長 prompt 結果差多少。

**繁中改寫：**
現在基本上不可能有人「直接給你看他的 prompt」了，因為一切都取決於參考資料、skills 和範例。

我常常先請 agent 去看我做過的另外三個 repo、上網找參考資料、呼叫其他 AI API 等等。

**核心概念（簡單說）：**
這點出 prompt engineering 已經演變成 context engineering。好結果的來源不再是一段文字，而是 agent 能取用的整套素材：你過去的程式碼（風格與慣例的最佳範本）、外部參考、可重用的 skills，以及其他工具的輸出。單獨抽出 prompt 就像只給別人看食譜的最後一步，卻沒給備料清單。

對開發者來說，這意味著「讓 agent 先看範例再動手」往往比寫更長的指示更有效，因為範例同時傳達了架構、命名、測試習慣等難以用文字描述的隱性知識。

**前端工程師實際應用：**
- **跟你工作的關聯：** 你過去做過的專案就是最好的 prompt。與其描述「我喜歡的資料夾結構和元件寫法」，不如直接指給 agent 看。
- **具體場景：** 開新的 Next.js 專案時，先說「先讀 `../dashboard-app` 和 `../marketing-site` 的 `app/` 與 `components/` 結構，參考它們的慣例建立這個新專案的骨架」，再補一句用 WebSearch 找 App Router 最新的 caching 寫法。
- **這週可以嘗試：** 整理一個你最滿意的 repo 當「範本 repo」，在其他專案的 `CLAUDE.md` 加一行「新增元件前先參考 `<路徑>` 的寫法」，看產出風格是否更一致。

**繁中改寫：**
Anthropic 正式推出 Claude Sonnet 5.5，這是 Claude 5.5 家族的第二個模型。相較 Sonnet 5 是明顯升級：輸出速度快 30% 以上，大多數工作的成本最多降低 30%。

定位上，Sonnet 5.5 是 Opus 5.5 更快、更便宜的搭檔：Opus 5.5 負責需要謹慎判斷的複雜工作，Sonnet 5.5 則擅長範圍明確的日常任務、修 bug，以及產出精緻的文件、簡報與試算表，而且很有設計眼光。主打大量、低成本場景的 Haiku 5.5 會在未來幾週加入。

效能方面，Sonnet 5.5 在 agentic coding 評測 Terminal-Bench 4.0 拿到 70.6%（Sonnet 5 只有 10.3%），甚至略高於 Opus 5.5；CursorBench 最佳分數只比 Opus 5.5 低約兩分；也是第一個只靠截圖就破關 Pokémon 紅版的 Sonnet 模型。價格和 Sonnet 5 相同（每百萬 input token $2、output $10、cache read $0.20），但完成同樣工作所需 token 少很多，實測每個任務最多便宜 30%。在低或中 effort 下，就能用約十分之一的成本超越 Sonnet 5 的最佳成績。

Coding 上的進步特別明顯：早期測試者稱讚它理解 codebase 很快，而且更常把 tool call 批次處理，步驟更少、成本更低。安全方面，因為資安能力已接近 Opus 5，它是第一個上線就帶有 cyber safeguards 的 Sonnet 模型，但一般軟體開發不受影響。

**核心概念（簡單說）：**
Sonnet 5.5 的重點不是「更強」而是「每塊錢買到的能力大幅提升」。Anthropic 用「分數 vs 每任務成本」的圖來說明：越靠左上角代表越划算，而 Sonnet 5.5 在低 effort 時就落在 Sonnet 5 最高 effort 點的上方。這讓模型選擇策略變得更清楚——Opus 5.5 處理開放式、需要長時間判斷的任務；Sonnet 5.5 則在明確任務上以更低 effort 快速完成。

另一個值得注意的技術細節是「批次 tool call」：agent 的成本很大一部分來自來回往返（讀一個檔、想一下、再讀下一個），Sonnet 5.5 傾向一次發出多個獨立的 tool call，減少回合數，這也是速度和成本同時改善的原因之一。

**前端工程師實際應用：**
- **跟你工作的關聯：** 官方特別點名 Sonnet 5.5「會替 UI 加上精緻度」，加上 CursorBench 接近 Opus 的表現，代表切版、元件實作、UI 微調等前端日常任務很適合交給它，成本與等待時間都更低。
