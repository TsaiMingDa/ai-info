## trq212 · X

**原文網址：** [https://x.com/trq212/status/2099958388230873165](https://x.com/trq212/status/2099958388230873165)

**原文：**
> I was not expecting things to go this way, but I think MCPs are better than CLIs for most integrations.
>
> The models have gotten much better at tool calling, we can defer tools & MCP is now stateless.
>
> If you need to compose/filter data, add params like query to your MCP tools.

**繁中改寫：**
我沒想到事情會這樣發展，但我認為對大多數整合場景來說，MCP 其實比 CLI 更適合。模型的 tool calling 能力已經進步很多，我們可以延遲載入工具（defer tools），而且 MCP 現在是 stateless（無狀態）的。如果你需要組合或過濾資料，可以在你的 MCP tools 裡加上像 query 這樣的參數。

**核心概念（簡單說）：**
這則貼文談的是「要用 CLI 還是 MCP 做工具整合」的取捨。過去大家常覺得寫一支 CLI 工具比較直觀、好除錯，MCP（Model Context Protocol）則顯得多一層抽象成本。但隨著模型的 tool calling（判斷該呼叫哪個工具、帶什麼參數的能力）大幅進步，加上 MCP 可以做到「defer tools」（不用一次把所有工具定義塞進 context，用到時才載入）以及「stateless」（不需要維護連線狀態），MCP 的優勢就顯現出來。他建議設計 MCP tool 時加上像 query 這種參數，讓模型自己組合、過濾資料，而不是回傳一整包資料再讓模型自己篩選，這樣能省 context、也更精準。

**前端工程師實際應用：**
- **跟你工作的關聯：** 如果你有在幫專案接 AI agent（例如串 Claude Code 或自己開發的 agent 功能），未來要決定包一支 CLI 給 agent 用，還是直接寫 MCP server，這則貼文給了明確方向：優先考慮 MCP。
- **具體場景：** 假設你要讓 AI agent 查詢公司內部的商品資料庫，與其寫一個回傳全部商品清單的 API 工具，不如設計一個 MCP tool，讓它接受 query、category、priceRange 等參數，模型呼叫時就能直接篩選出需要的資料，省下大量無用 token。
- **這週可以嘗試：** 找一個你現有專案裡「回傳一大包資料再讓前端/AI 自己篩」的 API endpoint，改成接受篩選參數的版本，體會一下輸出資料量變小、呼叫方判斷邏輯變簡單的差異。

**原文：**
> Salesforce in Claude is now available in beta.
>
> It brings your accounts, opportunities, and pipeline into Claude, with 37 pre-built sales skills. Prep a call, review a deal, create a pipeline dashboard, or send your forecast without leaving the conversation.

**繁中改寫：**
Salesforce in Claude 現在開放 beta 測試了。這項功能把你的客戶帳戶、商機（opportunities）與業務管線（pipeline）都整合進 Claude，並內建 37 個現成的業務技能（sales skills）。你可以直接在對話中準備會議、檢視交易進度、建立管線儀表板，或是送出業務預測，完全不用離開 Claude。

**核心概念（簡單說）：**
這是 Anthropic 把 Claude 跟 Salesforce（企業最常用的 CRM 系統之一）深度整合的產品發布。概念上是把「Skills」（可重複使用的技能／工作流程包）這個機制，套用在特定企業系統上：Anthropic 事先包裝好 37 個跟業務流程相關的技能，讓 Claude 能直接讀寫 Salesforce 裡的資料並執行操作，而不只是被動回答問題。這代表 Claude 正從「通用聊天助理」進一步走向「能直接操作企業系統的 agent」。

**前端工程師實際應用：**
- **跟你工作的關聯：** 如果公司內部也有類似需求（讓 AI 直接操作內部系統，而不只是查資料），這個案例是很好的參考架構：透過 Connector／Skills 機制把外部系統包裝成一組結構化的操作。
- **具體場景：** 假設你的公司用的是自家後台系統或另一套 CRM，可以參考這種「pre-built skills」的設計方式，用 Claude Agent SDK 或 MCP 把「建立客戶」、「查詢訂單狀態」、「產生報表」這類常見操作包成獨立技能，供內部 Claude 使用。
- **這週可以嘗試：** 去看一下 Claude 官方的 Connectors／Skills 文件，了解 Salesforce in Claude 底層大概是怎麼包裝技能與呼叫外部系統的，評估看看自己專案裡有沒有類似「重複性業務操作」可以用同樣模式包裝起來。

## Claude Code · Changelog

**版本號 / 日期：** 2.1.273 / September 15, 2026

**變更項目（精選重點，原文為英文）：**
- Added a notification when an MCP server disconnects mid-session and automatic reconnection gives up, pointing at /mcp（MCP server 連線中斷且自動重連失敗時，現在會跳通知並指向 /mcp 指令）
- Added forking a session started with claude --remote-control or /remote-control from the Claude app; the fork runs as a background session on your computer（可以從 Claude app 對一個以 --remote-control 啟動的 session 進行 fork，複製出的 session 會在你電腦上以背景 session 執行）
- Fixed the context meter and auto-compact counting advisor-tool turns at roughly twice their real context size, which made auto-compact fire at about half the real window（修正 context 計量與 auto-compact 把 advisor-tool 的回合算成約兩倍大小的問題，過去會導致 auto-compact 在實際還沒用滿一半 context 時就提早觸發）
- Fixed skills synced from claude.ai staying available after your organization turns Skills off; they now move to the recoverable trash（修正組織關閉 Skills 功能後，從 claude.ai 同步下來的 skills 仍可使用的問題，現在會移到可復原的垃圾桶）
- Fixed /tui refusing to restart because of an agent-team teammate that had already finished its work and was no longer shown in the agents panel（修正因為一個已完成工作、面板上已不顯示的 agent-team 隊友，導致 /tui 無法重新啟動的問題）
- Improved responsiveness in long sessions: hook progress and sub-agent activity no longer re-process the whole conversation on every update（改善長對話 session 的反應速度：hook 進度與 subagent 活動更新時不再重新處理整段對話）
- Changed auto mode on Bedrock, Vertex and Foundry to use the local classifier by default for now; set CLAUDE_CODE_AUTO_MODE_SERVER=1 to use the platform's server-side classifier（Bedrock/Vertex/Foundry 上的 auto mode 目前預設改用本機分類器，可設定 CLAUDE_CODE_AUTO_MODE_SERVER=1 改回平台端的伺服器分類器）
- [Code Review] Fixed /ultrareview --post so a retry after a GitHub error posts the findings comment exactly once instead of never or twice; the comment now names the reviewed commit（修正 /ultrareview --post 在 GitHub 發生錯誤後重試時，發現的留言只會貼一次，且會標明是針對哪個 commit 做的 review）

**核心概念（簡單說）：**
這個版本以修正（bug fixes）與體驗改善為主，其中最值得注意的是 context 計量與 auto-compact 的修正：過去因為把「顧問型工具（advisor-tool）」的回合算成兩倍大小，導致對話還沒真正用滿一半 context 就被提早壓縮（auto-compact），現在修正後長對話能撐得更久、更準確才觸發壓縮。另外也強化了長 session 的反應速度，以及 Remote Control session 的 fork 能力，讓你可以從手機／其他裝置上對一個遠端啟動的 session 做分支，分支後會在本機以背景執行。

**前端工程師實際應用：**
- **跟你工作的關聯：** 如果你常常用 Claude Code 開長時間、多輪的重構或除錯 session，這次 auto-compact 計量的修正會直接影響你能在一個 session 裡「撐多久」才被壓縮打斷上下文。
- **具體場景：** 之前你可能發現一個中大型專案的重構 session 做到一半，context 突然被 auto-compact，導致前面討論的細節被摘要掉、Claude 開始問已經講過的問題；這個版本修正後，同樣長度的對話理論上能撐更久才觸發壓縮。
- **這週可以嘗試：** 升級到 2.1.273（或更新版本）後，觀察一下平常會觸發 auto-compact 的長 session，看看是不是能比以前撐更多輪對話才被壓縮，藉此重新評估自己「主動 /compact」的時機。
