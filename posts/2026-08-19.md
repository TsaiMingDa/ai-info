## boris_cherny · X

**原文網址：** [https://x.com/bcherny/status/2089924199804711410](https://x.com/bcherny/status/2089924199804711410)

**原文：**
> The small quality of life improvements keep coming. When you're using Desktop every day, slow startup makes the app feel sluggish. Working on improving this even more!
>
> Quote — ClaudeDevs @ClaudeDevs:
> Claude Desktop now starts ~2x faster than it did a month ago.
>
> When the app started in the background, its timers got throttled and the JS engine dropped into power-saving mode. We now boot at full speed even while the window's still hidden, along with some smaller perf fixes!

**繁中改寫：**
Boris Cherny（Claude Code 團隊）轉發 ClaudeDevs 官方帳號的貼文並加碼分享：Claude Desktop 現在啟動速度比一個月前快了大約 2 倍。原因是應用程式在背景啟動時，作業系統會限流計時器（throttle timers）並讓 JS 引擎切換到省電模式，導致啟動變慢；團隊修正後即使視窗還沒顯示，也能維持全速啟動，同時附帶了一些其他效能微調。Boris 表示這類「日常持續使用會感受到差異」的小體驗優化還會持續推出。

**核心概念（簡單說）：**
這其實是 Electron / 桌面應用常見的效能陷阱：作業系統為了省電，會對背景視窗或非前景分頁的 JS 執行環境做節流（throttling），常見手法是降低 `setInterval`／`setTimeout` 的觸發頻率，或讓 JS 引擎進入低功耗模式。這對一般網頁沒差，但對「啟動流程本身就在背景執行初始化邏輯」的應用來說，就會讓啟動時間被平白拉長。解法通常是識別出啟動關鍵路徑，確保這段邏輯不會被丟進會被節流的計時器機制裡，改用不受背景節流影響的排程方式（例如某些平台的高優先權 timer API，或乾脆把關鍵路徑改成同步/立即執行）。

**前端工程師實際應用：**
- **跟你工作的關聯：** 如果你有做 Electron、Tauri 這類桌面應用，或是有背景分頁／背景視窗邏輯的 Web App，這種「背景時計時器被節流拖慢啟動或初始化」的問題很容易踩到，而且不容易在前景測試時發現。
- **具體場景：** 你的桌面 App 開機時常駐在背景（例如放在系統匣），使用者點開時卻要等好幾秒才有反應；用 Chrome DevTools Performance 面板側錄一次啟動流程，觀察 `setTimeout`/`setInterval` 的實際觸發間隔是否被拉長，就可能發現類似 Claude Desktop 遇到的節流問題。
- **這週可以嘗試：** 檢查自己專案裡「應用啟動時的初始化邏輯」有沒有包在會被背景節流影響的計時器裡；如果有，改成不依賴計時器觸發的方式（例如直接同步執行，或用 `requestIdleCallback`／平台原生的高優先權排程 API 取代一般 timer）。

**原文網址：** [https://x.com/bcherny/status/2089538781909332210](https://x.com/bcherny/status/2089538781909332210)

**原文：**
> Small quality of life improvements like this add up. More on the way
>
> Quote — ClaudeDevs @ClaudeDevs:
> Perf win of the day: Claude Code CLI now uses 2x less CPU at p99.
>
> Bun's garbage collector was running on a fixed timer, so it would kick in mid-turn and steal CPU right when Claude Code was busiest. Now it waits until the process is idle.

**繁中改寫：**
另一則 Boris 轉發 ClaudeDevs 的效能優化貼文：Claude Code CLI 在 p99（尾端延遲，也就是最差情況）的 CPU 使用率降低了 2 倍。問題根源是 Bun runtime 的垃圾回收（garbage collector, GC）原本是用固定時間間隔觸發，導致它常常在 Claude Code 正在忙著處理一輪對話（mid-turn）、CPU 最吃緊的時候跳出來搶資源；團隊把觸發時機改成「等到 process 閒置時才做 GC」，讓尖峰時的 CPU 使用率明顯下降。

**核心概念（簡單說）：**
這是一個經典的 runtime 效能問題：固定時間間隔觸發的 GC（time-based GC scheduling）雖然實作簡單，但完全不管當下系統忙不忙，容易在最不該打斷的時候插隊搶佔 CPU，造成尾端延遲（p99 latency）飆高——也就是大部分請求都很快，但少數請求會突然卡頓。解法是把 GC 觸發時機從「固定時間」改成「idle-triggered」（閒置時觸發），這樣可以避免在系統忙碌高峰期額外增加 CPU 負擔，讓效能曲線更平滑、可預期。這跟瀏覽器的 `requestIdleCallback` 概念是同一個思路：把非緊急的背景工作排到瀏覽器/runtime 判斷「現在有空」的時候再做。

**前端工程師實際應用：**
- **跟你工作的關聯：** 如果你的 Node.js／Bun 服務有明顯的 p99 延遲尖峰，卻找不到明確原因，GC 觸發時機是很值得懷疑的對象之一，尤其是高流量、CPU 密集的後端或 CLI 工具。
- **具體場景：** 你的 API 服務平均延遲很正常，但監控上偶爾會出現幾百毫秒的尖峰，用 `--trace-gc`（Node.js）或 Bun 的對應 flag 觀察 GC 觸發時間點，如果剛好都對到延遲尖峰，就代表你也遇到類似問題。
- **這週可以嘗試：** 幫自己維護的 Node.js／Bun 服務加上 GC 觀測（例如 `node --trace-gc` 或 `perf_hooks` 的 GC 事件監聽），把 GC 觸發時間點跟你的延遲監控疊圖比對一次，確認尖峰是不是跟 GC 有關。

**核心概念（簡單說）：**

**前端工程師實際應用：**
- **跟你工作的關聯：** 如果你的公司有 SaaS 產品，這則貼文點出一個值得思考的產品方向：你的服務有沒有辦法拆出一組「給 agent 用」的 headless 介面（例如 MCP server 或標準化 API），而不只是給人類用的網頁前端。
- **具體場景：** 假設你們做的是一個工單系統 SaaS，目前只有網頁介面給客服人員操作；可以評估把常用操作（建立工單、查詢狀態、指派負責人）包成一個 MCP server，讓客戶自己接的 AI agent（例如客服機器人）可以直接呼叫，並依呼叫次數或用量計費，而不是只賣人類帳號的月費。
- **這週可以嘗試：** 盤點一下你們產品裡「最常被重複執行的操作」，思考如果把它們包裝成一個獨立、無介面的 API 或 MCP tool，讓 agent 可以直接呼叫，會是什麼樣子；不用真的動工，先寫一份簡單的技術評估給 PM 參考。

**核心概念（簡單說）：**
Diffusion model 是「直接生成像素／畫面」，輸出的是不可編輯的圖片或影片本身；而 LLM coding model 走的是另一條路——它生成的是「產生這個畫面的程式碼／規則」（procedural generation，程序生成），例如寫一段 Remotion 動畫程式、寫一段 3D 場景生成邏輯、寫一段圖形演算法。這種方式的好處是輸出結果是可編輯、可參數化、可重複使用的：你可以改一個變數就得到無限變化，也可以精準控制每個細節，而不像 diffusion model 生成的內容常常「差不多但很難精準微調」。Thariq 的觀點是，這種「用程式碼描述創意」的方式，在很多創作任務上其實比直接生圖／生影片更有優勢。

**前端工程師實際應用：**
- **跟你工作的關聯：** 如果你的工作涉及動態視覺效果、資料視覺化、遊戲開發或創意編碼（creative coding），這個趨勢代表你可以用 Claude Code 直接生成程序化的視覺內容，而不需要依賴額外的圖像生成工具再手動整合。
- **具體場景：** 需要幫產品做一個有質感的載入動畫或背景視覺效果，與其去找 AI 生圖工具生成靜態素材再想辦法做成動畫，可以直接請 Claude Code 用 Canvas／SVG／Remotion 寫一段程序生成的動畫邏輯，得到的是可以隨螢幕尺寸、主題色動態調整的成果。
- **這週可以嘗試：** 找一個目前用靜態圖片或影片素材呈現的視覺效果（例如行銷頁的背景動畫），試著請 Claude Code 用程式碼（Canvas、SVG 或 CSS）重新生成一個程序化版本，比較兩種做法在檔案大小、可調整性上的差異。
