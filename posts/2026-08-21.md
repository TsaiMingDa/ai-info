**原文：**
> Small quality of life improvements like this add up. More on the way
>
> Quote — ClaudeDevs (@ClaudeDevs): Perf win of the day: Claude Code CLI now uses 2x less CPU at p99. Bun's garbage collector was running on a fixed timer, so it would kick in mid-turn and steal CPU right when Claude Code was busiest. Now it waits until the process is idle.

**繁中改寫：**
這種小小的體驗改善會慢慢累積起來，後面還有更多。（引用 ClaudeDevs：今日效能戰果——Claude Code CLI 在 p99 情況下 CPU 用量降低了一半。原因是 Bun 的 garbage collector 是用固定計時器觸發，導致它常常在 Claude Code 最忙碌、正在處理 turn 時跳出來搶 CPU。現在改成等到 process 閒置時才觸發 GC。）

**核心概念（簡單說）：**
這是典型的 GC（garbage collection）排程優化案例。Bun runtime 原本的 GC 是固定時間間隔觸發，不管當下 process 是否忙碌都會執行，導致關鍵運算路徑被迫讓出 CPU 給 GC。修正後改為等待 process idle 才觸發 GC，讓 CPU 尖峰負載時不會被打斷，實測 p99 CPU 使用量降低一半。

**前端工程師實際應用：**
- **跟你工作的關聯：** 如果你的專案用 Bun 或其他有自動 GC 的 runtime（Node.js 也有類似機制），「GC 搶佔忙碌線程」的問題在高頻運算或即時互動場景也可能發生。
- **具體場景：** 你的 Node.js/Bun 後端在處理高頻請求時，偶爾出現忽快忽慢的延遲尖峰（tail latency），這常常就是 GC 在不對的時間點觸發造成的。
- **這週可以嘗試：** 用 runtime 內建的 profiling 工具（例如 Node 的 `--trace-gc`）觀察你專案的 GC 觸發時間點，看是否跟效能尖峰負載重疊。
