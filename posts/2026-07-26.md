> Opus 5 has a better FrontierCode score at medium effort than higher effort - despite increasing performance with effort on other evals. Why?

**繁中改寫：**
Opus 5 在 FrontierCode 這個評測上，用「medium」努力程度（effort）反而比用更高的 effort 分數還高——但在其他評測上，effort 越高分數通常會越好。這是為什麼？

**核心概念（簡單說）：**
Claude 模型有個叫 effort（努力程度／推理強度）的參數，可以讓你選擇模型要花多少運算資源、想多久再回答，通常 effort 越高、答案品質越好。但這則貼文指出一個反直覺的例外：在 FrontierCode（程式碼相關評測）上，中等 effort 的表現反而優於高 effort，這暗示「想更久不一定寫出更好的程式碼」，可能是過度思考導致模型在某些程式任務上想太多、改太多，反而弄巧成拙。這是評估 AI 模型時常見的細節現象，值得開發者在調整 effort 參數時多加留意。

**前端工程師實際應用：**
- **跟你工作的關聯：** 如果你在用 Claude API 開發功能時會調整 effort/reasoning 參數，這提醒你「效果程度」不是越高越好，特別是程式碼生成類任務。
- **具體場景：** 假設你的 AI coding agent 預設用 max effort 來生成程式碼，但發現輸出品質不穩定或過度複雜，可以嘗試調降到 medium effort 做 A/B 測試。
- **這週可以嘗試：** 如果你的專案中有程式碼生成相關的呼叫，實際比較 medium 與 high/xhigh effort 在你自己任務上的表現差異，別預設「越高越好」。

**核心概念（簡單說）：**
System prompt 是每次對話開始前先「餵」給模型的一大段隱藏指令，用來設定模型的行為規則。過去模型能力較弱時，工程師習慣寫又臭又長的 system prompt，把各種邊角案例、規則都塞進去，靠大量文字硬性規範模型行為。但隨著 Claude 5 世代模型的推理和判斷能力大幅提升，這篇文章指出：這套「塞好塞滿」的做法反而會拖累新模型表現，因為模型已經足夠聰明，能自己判斷情境，過長的 prompt 反而製造雜訊、稀釋真正重要的指示。Anthropic 自己把 Claude Code 的 system prompt 砍掉八成，正是在實踐這個新原則。

**前端工程師實際應用：**
- **跟你工作的關聯：** 如果你的專案有寫過又長又細的 system prompt 或 Claude.md（給 Claude Code 用的專案說明檔）來「控制」Claude 的行為，這則貼文直接點出這套做法可能已經過時，值得重新檢視。
- **具體場景：** 假設你的 Claude Code 專案裡 CLAUDE.md 塞了大量條列式規則（像是「一定要先做 X 才能做 Y」「遇到 Z 情況要怎樣」），可以試著砍掉一半，只留下真正關鍵、非顯而易見的規則，看看模型表現是否反而更穩定。
- **這週可以嘗試：** 檢查自己專案的 CLAUDE.md 或 system prompt，找出哪些指示其實是「模型自己就該知道」的常識，先砍掉這些贅字，再觀察 Claude 5 系列模型的實際輸出品質有沒有變化。

Opus 5 對科學研究來說也是實質進步，在結構生物學、有機化學、生物資訊學等生命科學評測上全面優於 Opus 4.8，尤其在有機化學（從光譜資料推斷分子結構，內部評測高出 10.2 個百分點）與蛋白質相關任務（預測蛋白質序列變異如何影響功能，高出 7.7 個百分點）上進步最明顯。

在「與 Opus 5 合作」方面，這個模型更擅長驗證自己的工作、耐心迭代直到成功。例如：在一個 Frontier-Bench 任務中，模型拿到一張機械零件的圖，卻被刻意設計成無法直接「看到」這張圖，Opus 5 自己寫了一套電腦視覺 pipeline 從原始像素中拉出幾何資訊，重建出完整零件，而且能重複做到——同樣條件下，其他競品模型嘗試五次都做不到。另一個案例中，面對一個熱門開源套件管理工具的真實 bug，Opus 5 找到了根本原因並修好了社群修補程式漏掉的邊角案例，而競品模型只修掉表面症狀就回報「已解決」。還有一位交易公司的工程師，用 Opus 5 在單一 session 內就建好一個新交易所的市場資料 feed，過去模型即使給了詳細計畫也做不到；由於找不到即時 feed 可以驗證，Opus 5 甚至自己蓋了一套測試工具來確認資料解析正確。

來自早期存取客戶的評價涵蓋 Devin、Cursor、Zapier、Lovable、Box 等公司，普遍指出 Opus 5 相較 Opus 4.8 有明顯的品質、穩定性與效率提升，例如 Zapier 提到 Opus 5 在 AutomationBench 上拿到 100% 通過率、Box 提到資料分析任務進步 11%、due diligence 任務進步 17%。

在對齊（alignment）與安全性方面，Opus 5 是 Anthropic 目前為止對齊程度最高的模型：更符合 Claude's Constitution、欺騙行為比例最低、最不容易被誘導做出濫用行為，也是目前避免不可逆風險行為做得最好的模型。安全性上，Opus 5 並未推進資安、生物風險等雙重用途能力的前緣，在資安漏洞開發（exploit）能力上仍明顯落後 Mythos 5，即使找漏洞的能力已經接近。

Opus 5 今天起在所有平台上架，輸入每百萬 token 5 美元、輸出每百萬 token 25 美元，價格與 Opus 4.8 相同；開發者可以在 Claude API 上使用 `claude-opus-5`。同時，Anthropic 也釋出兩項 beta 功能：對話中途可以更換 Claude 能使用的工具而不會讓 prompt cache 失效；API 上可以設定自動 fallback，被安全分類器擋下的請求會自動轉給其他可用模型，而不是直接被封鎖。

**核心概念（簡單說）：**
這是 Anthropic 最新一代 Opus 模型的正式發布公告。可以把 Opus 系列理解成「效能與成本的甜蜜點」：不像最頂級的 Fable 5 那麼貴，但這次 Opus 5 的表現已經逼近 Fable 5 的水準，等於是用一半價格買到接近頂規的能力。文章的重點資訊分三塊：第一，效能大幅提升，尤其在程式碼撰寫、電腦操作（computer use）、業務流程自動化這幾類「agentic」任務上進步最多；第二，模型變得更會「自我把關」——遇到看不到的資訊會自己想辦法補（例如自建電腦視覺 pipeline），修 bug 會抓根本原因而不是治標，這代表可以放心交付更複雜、更少人工監督的任務；第三，安全與對齊程度也同步提升，且刻意維持在資安攻擊能力上落後於專用的 Mythos 5 模型，避免雙重用途風險。對開發者來說，最實際的變化是：同樣價格，拿到更強、更可靠的 Opus 模型，而且新增了「換工具不必重算 prompt cache」「安全分類器自動 fallback」兩個平台功能，讓串接體驗更順。

**前端工程師實際應用：**

- **具體場景：** 假設你在做一個內部的自動化測試 agent，過去用 Opus 4.8 常常在遇到「沒有直接資料來源可以驗證」的情境時卡住或亂猜，Opus 5 展現出的「自己動手建驗證工具」能力，代表這類流程的成功率可能明顯提升。
- **這週可以嘗試：** 把你專案裡呼叫 `claude-opus-4-8` 的地方換成 `claude-opus-5`，重新跑一次原本效果不理想的 agentic 任務（尤其是程式除錯、資料驗證類的），並試試新的「mid-conversation tool changes」beta 功能，看看能否減少換工具造成的 prompt cache 失效問題。
