## boris_cherny · X

**原文網址：** https://x.com/bcherny/status/2071379474277613732

**原文：**
> As engineering, product, design, DS, etc. melt into a new kind of role, I was reflecting on what roles might look like in the future. For example, when I look at the Claude Code team I see what I think is five archetypes:
>
> 1. Prototyper: comes up with brand new ideas; churns out many ideas, most of which don't ship
> 2. Builder: quickly turns a prototype/idea into production-grade product/infra
> 3. Sweeper: cleans up the UI, simplifies the code and system, unships, optimizes performance
> 4. Grower: takes a product that has been built and iterates on it to improve Product-Market Fit
> 5. Maintainer: owns a mature system to make it secure, reliable, fast, and efficient as it scales
>
> Many people span across 2 roles, and sometimes 3 roles. I also notice that these roles are not really tied to job function -- eg. across Anthropic, some designers match category 1, some 2, some 3; same for engineers, PM, DS.
>
> A healthy team needs a mix of these, depending on the product:
> - A product that is new and pre-PMF needs people that are strong at 1+2+3
> - A product that is growing and has found PMF needs 2+3+4 and some 5
> - A product that has strong PMF needs 3+4+5 and some 2
>
> Maybe product roles of the future will look more like this, and less like the domain-specific roles of today?

**繁中改寫：**
工程、產品、設計、資料科學等職能正在融合成某種新型角色，Boris Cherny 思考未來的角色樣貌會是什麼。以 Claude Code 團隊為例，他觀察到五種原型：Prototyper（原型快速衝量）、Builder（把原型做成正式產品）、Sweeper（清理 UI、精簡系統）、Grower（找到 PMF 後持續優化）、Maintainer（維護成熟系統的安全與效能）。他認為這些角色不只限於特定職能，設計師、工程師、PM 都可能屬於任何一種原型，而且健康的團隊需要依產品所在階段搭配對的組合。

**核心概念（簡單說）：**
Boris 提出了一套跨職能的「貢獻者原型」框架，核心洞察是：未來人們的工作方式不再以職稱（工程師 / 設計師 / PM）做區分，而是以他們在產品生命週期中扮演的角色定義自己。這就像球隊分工：有人專門開球（Prototyper）、有人負責把進攻轉換為得分（Builder）、有人掃空間讓隊形更緊（Sweeper）、有人維持得分節奏（Grower）、有人鞏固防線（Maintainer）。

這個框架也點出一個管理啟示：把團隊組成想成「這五種原型的比例」比「頭銜湊齊了嗎」更有洞察力，尤其在 AI coding agent 讓純寫程式的門檻降低之後，角色分工可能真的會往這個方向轉移。

**前端工程師實際應用：**
- **跟你工作的關聯：** 前端工程師傳統上偏 Builder + Sweeper，但 AI 工具出現後，Prototyper 的能力門檻大幅降低——你現在可以快速用 Claude Code vibe coding 出原型，不再需要等設計師或後端先動。
- **具體場景：** 你下週要提新功能方案時，可以先用 Claude Code 在一個 Next.js sandbox 做 Prototyper 的工作（快速拼出三個可互動的 UI 原型），再作為 Builder 把選定方向做扎實，最後戴上 Sweeper 帽子砍掉重複的 component。
- **這週可以嘗試：** 花 30 分鐘，用 Claude Code 或 v0.dev 直接 vibe coding 一個你平常需要先寫 PRD 才敢動的功能原型，感受一下當 Prototyper 是什麼感覺，再決定它值不值得進 Builder 階段。

## Claude Code · Changelog

**版本號 / 日期：** 2.1.195 / June 26, 2026（本週最新版本，自上次 digest 後無新版本發布）

**變更項目：**
- Added `CLAUDE_CODE_DISABLE_MOUSE_CLICKS` 環境變數：在全螢幕模式停用滑鼠點擊 / 拖曳 / hover，但保留滾輪捲動
- Fixed hook matchers with hyphenated identifiers（如 `code-reviewer`、`mcp__brave-search`）誤用子字串比對的問題，現在改為精確比對（exact-match）；如要比對整個 MCP server 的所有工具，改用 `mcp__brave-search__.*`
- Fixed macOS 語音聽寫（voice dictation）在長時間 session 後預設輸入裝置改變時錯誤擷取靜音
- Fixed 語音聽寫自動送出（auto-submit）在無空格語言（日文、中文、泰文）永遠不觸發的問題
- Fixed 僅由專案層 `.claude/settings.json` 啟用的 external plugin 每次載入都要求安裝同意的問題
- Fixed `/plugin Enable/Disable` 當 plugin 的 `plugin.json` name 與 marketplace entry name 不同時無法正常運作
- Fixed background jobs 在以較新版 Claude Code 寫入時消失或遺失資料
- Fixed 重新開啟崩潰的 background task 時出現最長 5 秒空白畫面
- Fixed background agent daemon 的控制 socket 啟動失敗時以不可達狀態運行阻塞重啟的問題
- Improved Linux 語音模式：現在能區分「沒有麥克風」與「SoX 未安裝」（SoX 存在但無音訊擷取裝置時）
- Improved `claude agents` 完成清單：填滿可用垂直空間；在小終端機下標題會精簡顯示以讓 live session 保持可見
- Improved Remote session 啟動：容器啟動期間顯示 provisioning checklist

**核心概念（簡單說）：**
這版主要是 bug fix 和細節改善。最值得注意的是 **hook matcher 精確比對修正**：如果你的 `.claude/settings.json` 有設定 hooks 過濾器，且你使用了帶 `-`（連字號）的 MCP server 名稱，這個 fix 會改變你的 hook 觸發行為——以前 `mcp__brave-search` 會誤觸含這個字串的所有 tool，現在改為精確比對。語音聽寫的修正對多語言使用者（尤其中文）也很重要。

**前端工程師實際應用：**
- **跟你工作的關聯：** 如果你有使用 Claude Code hooks 搭配帶連字號的 MCP server（例如 `mcp__brave-search`），需要立刻檢查你的 hook matcher 是否還能觸發——精確比對可能導致原本有效的 pattern 失效。
- **具體場景：** 在 `.claude/settings.json` 裡，把 `mcp__brave-search` 改成 `mcp__brave-search__.*`，確保你的 hook 仍能比對到該 MCP server 旗下的所有工具。
- **這週可以嘗試：** 執行 `claude --version` 確認你已升級到 2.1.195，然後開啟 `/permissions` 查看 recent denials，確認 auto-mode 的行為符合預期。
