## trq212 · X

**原文網址：** https://x.com/trq212/status/2120223476279869875

**原文：**
> we need fewer one shot demos and more tools that show how you can collaborate with models to bring your vision to life
>
> （引用 @araminta_k：A few folks asked to see how I use the AI Assisted Tween & Paint harnesses, so I put together a little video with Claude! Linking below the workbook :)）

**繁中改寫：**
我們需要的不是更多「一次 prompt 就生成」的炫技 demo，而是更多能展示「你怎麼跟模型一起協作、一步步把腦中想像做出來」的工具。（他引用的是 Araminta 分享自己如何用 AI 輔助補間動畫與上色的 harness，並和 Claude 一起剪了一支教學影片。）

**核心概念（簡單說）：**
「one-shot demo」是指丟一句 prompt、模型直接吐出完整成品的展示，看起來很驚豔，但真實創作很少一次到位。Thariq 想強調的是「協作迴圈」：人提供方向與品味，模型負責大量重複勞動（像動畫的補間 in-betweening、上色），人再檢查、修正、重來。好的 AI 工具應該把這個迴圈設計得順手——可以局部重做、可以保留人的修改、可以看到中間狀態——而不是只追求單次輸出的驚豔度。

這其實跟前端開發很像：好的 dev tool 不是「一鍵生成整個 app」，而是像 HMR 一樣讓你改一點、立刻看到、再改一點的快速回饋。

**前端工程師實際應用：**
- **跟你工作的關聯：** 你在用 Claude Code 寫 UI 時，與其期待一個 prompt 生出完整頁面，不如把流程拆成「骨架 → 互動 → 細節樣式 → a11y」的多輪協作，每輪都由你驗收。
- **具體場景：** 做一個 Storybook 元件庫時，先讓 Claude 產出元件 API 與 stories，你在 Storybook 裡看過、調整 props 命名後，再請它補上 variants 與 Playwright 視覺回歸測試；每一步都留 commit，方便回滾。
- **這週可以嘗試：** 下一次請 AI 做 UI 時，刻意把任務切成三輪以上，並在每輪結束時寫下「我改了什麼、為什麼」，觀察最終品質是否比一次生成好。

## claudeai · X

**原文網址：** https://x.com/claudeai/status/2120206365759094857

**原文：**
> Starting to roll out today: Claude Whiteboards, Claude Sheets and Claude Data.
>
> Think a plan through on a board, build a tracker in a sheet, and tell a story with your data.

**繁中改寫：**
今天開始陸續推出：Claude Whiteboards、Claude Sheets 和 Claude Data。在白板上把計畫想清楚、用試算表建一個追蹤表、再用資料說一個故事。

**核心概念（簡單說）：**
Claude 從「對話 + 文件」延伸到三種新的協作載體：白板（視覺化發想）、試算表（結構化資料與計算）、資料呈現（圖表與資料敘事）。重點不是 Claude 多了三個 App，而是輸出格式從純文字變成「可以繼續編輯、團隊共用的活物件」——Claude 產出的是起點，人可以接手改，Claude 也能再回來改。

可以類比成前端的「從靜態 HTML 到可互動元件」：以前 AI 給你一段 markdown 表格，現在給你一個真的能排序、能加公式、能多人編輯的 spreadsheet。

**前端工程師實際應用：**
- **跟你工作的關聯：** 前端常需要整理元件清單、遷移進度、bug 追蹤，這些以前散落在 Notion / Google Sheets，現在可以直接在 Claude 裡生成並持續維護。
- **具體場景：** 準備把專案從 Webpack 遷到 Vite 時，請 Claude Sheets 依 `src/` 結構建一張遷移追蹤表（檔案、使用的 loader、負責人、狀態），再用 Claude Whiteboards 畫出 build pipeline 新舊對照，給團隊 review。
- **這週可以嘗試：** 若你是付費方案，挑一個正在進行的小專案，請 Claude 建一張 tracker sheet，觀察它產出的欄位設計是否比你手動建的更完整。

**原文：**
> With Claude Whiteboards, talk through a messy plan and Claude lays it out on a board your team can edit. With Claude Sheets, ask for a tracker or a budget and you get a working spreadsheet you can all keep building.
>
> In beta on paid plans.

**繁中改寫：**
有了 Claude Whiteboards，你可以把一團亂的計畫用講的講一遍，Claude 會幫你整理成一張團隊都能編輯的白板。有了 Claude Sheets，只要說你要一張追蹤表或預算表，就會拿到一份真的能用、大家可以繼續接手擴充的試算表。目前以 beta 形式開放給付費方案。

**核心概念（簡單說）：**
這則說明了兩個產品的核心互動：「非結構化輸入 → 結構化、可共編的輸出」。Whiteboards 把口語化、跳躍的想法轉成有節點與連線的版面；Sheets 把一句需求轉成有欄位、公式的「working spreadsheet」——關鍵字是 working，表示不是貼一張靜態表格，而是有公式、可運算的真試算表。「your team can edit」與「you can all keep building」則強調多人協作，Claude 產出後所有權回到團隊手上。

**前端工程師實際應用：**
- **跟你工作的關聯：** Sprint planning、技術債盤點、元件設計討論這類「先亂想再收斂」的會議，可以用 Whiteboards 即時整理成視覺化結構，省去會後整理筆記的時間。
- **具體場景：** Design review 時把「這個 Modal 要支援哪些狀態、哪些 a11y 需求、跟哪些 API 互動」直接口述給 Claude，讓它在 Whiteboard 上拆成 state、props、事件流三區，會後直接拿來寫 TypeScript 型別。
- **這週可以嘗試：** 下次技術討論會前，先把你的零散想法丟給 Claude Whiteboards 整理成一張板，會議直接從板子開始討論，比較效率差異。
