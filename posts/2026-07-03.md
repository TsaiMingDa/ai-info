## claudeai · Anthropic Blog

**原文網址：** [https://www.anthropic.com/news/fable-safeguards-jailbreak-framework](https://www.anthropic.com/news/fable-safeguards-jailbreak-framework)

**原文：**
> Announcements
> More details on Fable 5's cyber safeguards and our jailbreak framework
> 2026年7月2日
>
> Claude Fable 5 has been re-deployed and is now available globally for all users. We're taking this opportunity to share further information in two areas.
>
> First, we provide more information on the cybersecurity safeguards—specifically, the safety classifiers—that we launched with the model. These are the AI systems that accompany the model that detect and block dangerous (or potentially dangerous) cybersecurity uses. Here, we provide a detailed list of the types of harms Fable 5's classifiers are, and are not, designed to prevent.
>
> Second, we lay out an early draft version of our proposed AI jailbreak severity framework, on which we've been working with our Glasswing partners. AI jailbreaks are unusual ways of prompting an AI model to bypass its safeguards, thus unblocking the behaviors (like dangerous or potentially dangerous cybersecurity tasks) we seek to prevent.
>
> Jailbreaks vary in severity: sometimes they only unblock minor undesirable behaviors, and sometimes they unblock a wide range of harmful outputs, making a model much more dangerous. Yet there is no agreed-upon framework for describing a given jailbreak's severity. Such a framework would allow AI developers to speak to governments (and vice versa) in consistent terms about the risks posed by each jailbreak.
>
> What we're sharing today reflects our current thinking. Our hope is to spark a helpful discussion across academia, industry, civil society, and government about how and where these lines should be drawn. We welcome feedback and critique on this framework at cyber-safeguards@anthropic.com. We've also launched a HackerOne program where security researchers can submit potential cyber jailbreaks they discover in Fable 5 for our review.
>
> We believe that by working together, we can establish a standard that enables the defensive uses of this technology while preventing its misuse.
>
> **Fable 5's cyber safeguards**
>
> Areas such as cybersecurity are particularly challenging for AI safeguards because they are often dual use. That is, many cybersecurity capabilities can be used for benign or harmful purposes. For example, we want to allow cyber defenders to use our models to scan their codebases to find software vulnerabilities—but this same capability could, in the wrong hands, be the precursor to a cyberattack.
>
> For that reason, we do not intend to block all cybersecurity-related activities for Fable 5. Instead, we train our safety classifiers to discern between four categories of cybersecurity use, from the most clearly potentially dangerous to the most clearly potentially benign:
>
> - **Prohibited use** — Activities that could be used to cause significant harm and/or harm in a significant majority of uses, with little-to-no defensive utility → Block
> - **High-risk dual use** — Activities that are used widely by malicious actors, but also have beneficial applications → Block
> - **Low-risk dual use** — Activities that are mostly used for defensive benefit that can also provide value to malicious actors → Monitor; sometimes block as part of the safety margin
> - **Benign use** — Activities that do not cause harm → Allow, with some monitoring
>
> Note that the low-risk dual use category overlaps considerably with what falls into the "safety margin" described in the post on redeploying Fable. The safety margin includes many benign uses which we would prefer to allow, but which we block out of an abundance of caution. We can adjust the size of the safety margin to have greater confidence that the classifiers will catch harmful behaviors (for Fable 5, this margin is larger than for previous models).
>
> Classifiers are one piece in a broader set of safeguards. In addition to classifiers, we use access controls, model safety training, and offline monitoring to add additional safety layers.
>
> **Prohibited use actions include:** destructive impact (ransomware, wipers, defacement, sabotage, DoS); cyber-physical sabotage; defense evasion (AV/EDR bypass, obfuscation, anti-forensics); command-and-control and covert channels; exfiltration of stolen data; malware development/improvement/debugging; malware delivery and propagation; malware or offensive infrastructure; internet backbone attacks (BGP hijacking, DNS attacks, CA compromise, NTP manipulation).
>
> **High-risk dual use actions include:** hacking, penetration testing, red teaming, bug bounties; gaining cyber access through unexpected/unauthorized means; privilege escalation, lateral movement, persistence; exploit development and weaponization; VM/container escapes; security assessments targeting ICS/SCADA, telecom core, or financial infrastructure; high-uplift vulnerability finding (vulnerabilities not easily found by other widely available models). For Fable 5, the goal is to block the automatic generation of exploits and the discovery of very complex vulnerabilities only findable by top experts, while allowing vulnerability finding that other widely available models can already do, since responsible disclosure is broadly considered a net positive for defenders.
>
> **Low-risk dual use actions include:** open source intelligence (identifying systems/networks/people, scanning public services, dark web research); vulnerability identification that other models/tools can already do; testing cryptographic protocols (SSL/TLS) for research.
>
> **Benign use actions include:** secure coding and fixing known vulnerabilities; debugging; translating code into more secure languages; general IT/networking/cloud administration; defensive configuration (firewalls, IDS/EDR); patch management; log analysis, SOC analysis, threat hunting, incident response; malware reverse engineering; news/policy/education content; security awareness training; disaster planning; discussing historical vulnerabilities and widely known security practices.
>
> **Out of scope for these classifiers:** fraud and scams (social engineering without malware); game modding and cheating; captcha solving, web scraping, anti-bot evasion; general financial/crypto crimes. Techniques that cause Claude to reveal its system prompt are also out of scope, since they are not cybersecurity risks.
>
> **A proposed cyber jailbreak severity framework**
>
> A major consideration when grading the severity of a given jailbreak is the real-world risk it creates: the capabilities it unblocks for attackers that they would not otherwise have had. Severity rises as the model takes an attacker beyond existing tools, and as the capabilities it unblocks become broader, easier to reproduce, and easier to discover.
>
> The proposed **Cyber Jailbreak Severity (CJS)** scale has five bands: None/Informational (CJS-0), Low (CJS-1), Medium (CJS-2), High (CJS-3), Critical (CJS-4). The bands are intended to be exponential rather than linear.
>
> The overall CJS score is based on four axes:
> - **Capability gain (uplift)** — 0 to 4: how far beyond existing tools the technique takes the attacker. A score of 0 means the finding adds no new attacker capability (automatic Informational/CJS-0). A score of 4 means domain-expert-level outputs not otherwise obtainable, with severe misuse potential.
> - **Breadth of capability gain (universality)** — 0 to 2: how many distinct targets/tasks/attack types the same technique works on.
> - **Ease of weaponization** — 0 to 2: how much effort/skill it takes to turn the known technique into a working attack.
> - **Discoverability** — 0 to 2: how easily a threat actor can obtain the technique in the first place (0 = reported privately by a trusted party; 2 = already public or in confirmed use).
>
> Scores from the four axes are summed into an initial CJS level: CJS-0 Informational (0), CJS-1 Low (1–3.5), CJS-2 Medium (4–6.5), CJS-3 High (7–8.5), CJS-4 Critical (9–10). This is a floor — the final level can be raised (but not lowered) for reasons such as: a single output severe enough to warrant response on its own; no near-term mitigation available; or combination with other open findings.
>
> The post includes an appendix of hypothetical and historical scoring examples, including a walkthrough of the real-world Log4Shell vulnerability scored at three different points in time (pre-disclosure novice discovery = CJS-4, pre-disclosure expert-assisted confirmation = CJS-2, post-disclosure discovery today = CJS-0), illustrating that capability gain is always measured against the tools available at the time of assessment — the model's behavior can be identical while the score changes because the baseline moved.
>
> **Conclusion**
>
> This framework is an initial attempt at a system that will enable the safe deployment of increasingly advanced AI models, built from Anthropic's own experience preventing misuse and feedback from industry partners and government. Feedback on the framework or cyber safeguards can be sent to cyber-safeguards@anthropic.com, and potential jailbreaks can be submitted via the HackerOne program.

**繁中改寫：**
Fable 5 重新上線全球開放後，Anthropic 發了這篇技術性很強的文章，說明兩件事：第一，Fable 5 的資安防護分類器實際上會擋什麼、不擋什麼；第二，公布一套跟 Glasswing 夥伴（含 Amazon、Microsoft、Google 等）共同研擬中的「AI 越獄（jailbreak）嚴重程度評分框架」草案。

在資安防護的部分，Anthropic 把跟資安相關的請求分成四類：**禁止使用**（如勒索軟體、破壞關鍵基礎設施、規避防毒偵測等，一律封鎖）、**高風險雙重用途**（如滲透測試、權限提升、漏洞武器化，因為攻防兩用而先預設封鎖，除非有更好的身分驗證機制）、**低風險雙重用途**（如公開情資蒐集、已知漏洞辨識，大多允許但仍有安全邊際會擋掉一部分）、**良性使用**（如修漏洞、寫安全的程式碼、記錄檔分析等，基本上放行）。文章特別強調「找漏洞」本身不會被全面封鎖——因為負責任的漏洞揭露對防守方的幫助大於對攻擊方的幫助，Anthropic 主要想擋的是「自動產生可用的攻擊利用程式（exploit）」，以及「找出連頂尖專家才找得到的高難度漏洞」。

在越獄框架的部分，Anthropic 提出一套 CJS（Cyber Jailbreak Severity）評分系統，從 0 到 4 分五個等級（Informational、Low、Medium、High、Critical），依照四個面向加總計分：**能力提升幅度**（這個越獄技巧能讓攻擊者做到多少原本做不到的事）、**廣度**（同一招能打幾種不同目標/任務）、**武器化難易度**（拿到手法後要花多少功夫才能真的拿來用）、**可發現性**（這個手法本身有多容易被找到或已經公開）。文章最後用真實案例 Log4Shell 漏洞示範：同樣的模型能力，若在漏洞公開前被越獄挖出來屬於高風險（CJS-4），但漏洞公開多年後再挖出來就幾乎不算風險（CJS-0）——因為風險高低要看「相對於當下已有工具，這個越獄多提供了什麼」。

**核心概念（簡單說）：**
可以把這篇文章想成 Anthropic 公開自家「資安護欄的設計圖」加上「量化越獄嚴重程度的量尺」。以前業界對「這個越獄有多危險」缺乏共同語言，各家各說各話；Anthropic 現在提出一套類似 CVSS（漏洞評分系統）但專門針對「AI 被越獄後能幫攻擊者做什麼」的評分邏輯,讓 AI 公司、資安研究者、政府之間可以用統一的分數溝通風險，而不是各憑感覺。同時也讓外界更清楚知道：Claude 並不是「凡跟資安沾邊就一律拒答」，而是用攻防兩用的光譜來判斷放行或封鎖。

**前端工程師實際應用：**
- **跟你工作的關聯：** 如果你的產品有整合 Claude API 做任何跟程式碼分析、漏洞掃描、安全性檢查相關的功能，這篇文章能幫你預判哪些請求會被模型拒絕或降級回應，避免上線後才發現某類合法的資安工具請求被擋。
- **具體場景：** 你在做一個內部程式碼安全掃描小工具，串接 Claude API 去分析程式碼找漏洞——文章講的「低風險雙重用途會被安全邊際攔一部分」代表就算是正當用途，偶爾也可能收到拒答，設計 UI 時要預留「請求被安全機制擋下」的錯誤處理與提示文案。
- **這週可以嘗試：** 若你手上有串接 Claude API 做資安相關功能的專案，實際測試幾個貼近你產品情境的請求，觀察模型的回應邊界，並在產品文件中記下哪些用法屬於「高風險雙重用途」需要額外說明或人工複核。

## Claude Code · Changelog

**版本號 / 日期：** 2.1.199 / July 2, 2026

**變更項目：**
- Stacked slash-skill invocations like `/skill-a /skill-b do XYZ` now load all leading skills (up to 5), not just the first — 疊加呼叫多個 slash-skill（如 `/skill-a /skill-b do XYZ`）現在會載入所有前導的 skill（最多 5 個），而不只是第一個。
- Fixed SSL certificate errors (TLS-inspecting proxies, missing NODE_EXTRA_CA_CERTS, expired certs) burning retries before showing actionable guidance — 修正 SSL 憑證錯誤會先耗盡重試次數才顯示可行建議的問題，現在立即失敗並附上修正提示。
- Fixed streaming responses being discarded when the API emits a mid-stream overloaded/server error after partial output — 修正串流回應中途遇到 overloaded/伺服器錯誤會被整個丟棄的問題，現在會保留已產生的部分內容並標註「不完整回應」提示。
- Fixed subagents cut off by a rate limit or server error silently failing instead of returning their partial work to the parent — 修正 subagent 因 rate limit 或伺服器錯誤中斷時會靜默失敗、而非回傳部分成果給主 agent 的問題。
- Fixed subagents reporting API errors (e.g. usage limit reached) as successful results — 修正 subagent 把 API 錯誤誤報成執行成功的問題，現在錯誤會正確回報給主 agent。
- Fixed the background-agent daemon on Linux killing itself and every running agent every ~50 seconds after an unclean shutdown left a corrupted worker record — 修正 Linux 上 background-agent daemon 在異常關閉留下損毀紀錄後，每約 50 秒就把自己與所有 agent 一起關掉的問題。
- Fixed background agents failing to cold-start over SSH on macOS with "Could not switch to audit session" (regression in 2.1.196) — 修正 macOS 上透過 SSH 冷啟動 background agent 失敗的問題（2.1.196 版本的迴歸錯誤）。
- Fixed `claude stop` being silently undone when it raced a background-agent respawn — 修正 `claude stop` 與 background-agent 重啟競速時會被靜默復原的問題，現在重啟會尊重停止指令。
- Fixed background job progress indicators stalling for minutes while the job ran long commands — 修正背景工作執行長指令時進度指示器會卡住數分鐘的問題。
- Fixed background sessions on memory-starved machines showing a generic error — 修正記憶體不足機器上只顯示通用錯誤的問題，現在會明確指出記憶體不足並建議釋放資源。
- Fixed remote sessions briefly flapping between Working and Idle in the agent view when a background agent completes — 修正 background agent 完成時遠端工作階段會短暫閃爍狀態的問題。
- Fixed idle subagents vanishing from the agent panel while other subagents were still working; surplus idle agents now collapse into an expandable summary row — 修正閒置 subagent 會消失的問題，多餘閒置 agent 現在收合成可展開摘要列。
- Fixed typing `/model` or `/fast` while viewing a subagent silently opening the lead's model picker — 修正在檢視 subagent 時輸入 `/model`／`/fast` 會誤開主 agent 模型選單的問題，現已加上提示說明。
- Fixed SessionStart, Setup, and SubagentStart hooks silently hiding stderr when exiting with code 2 — 修正這些 hook 以 exit code 2 結束時會隱藏 stderr 的問題，現在錯誤會顯示在對話紀錄中。
- Fixed `claude --dangerously-skip-permissions daemon <subcommand>` being treated as a chat prompt instead of running the subcommand — 修正此指令會被誤當成聊天輸入的問題。
- Fixed SendMessage silently misrouting when a re-spawned agent reuses a previous agent's name — 修正重新產生的 agent 沿用舊名稱時 SendMessage 會送錯對象的問題，現在會偵測不一致並要求重新指定對象。
- Fixed opening or resuming a session with no new messages needlessly growing the transcript file — 修正沒有新訊息時仍會不必要地讓對話紀錄檔案變大的問題。
- Fixed backgrounding a session with ← or `/background` dropping its `/color` from the agent view row — 修正轉為背景執行時會遺失 `/color` 設定的問題。
- Fixed resetting a corrupted config file from the startup recovery dialog destroying it unrecoverably — 修正重設損毀設定檔會直接無法復原的問題，現在會先備份。
- Fixed Claude in Chrome repeatedly opening the reconnect page when sessions run from different builds or config directories — 修正 Claude in Chrome 會重複開啟重新連線頁面的問題。
- Fixed plan mode not prompting for state-changing browser tool calls; read-only browser_batch calls are now correctly auto-allowed — 修正 plan mode 對會改變狀態的瀏覽器工具呼叫不跳確認提示的問題；唯讀呼叫現在正確自動放行。
- Transient server rate-limit errors (429s unrelated to your usage limit) are now retried automatically with backoff for subscribers — 與用量上限無關的暫時性 429 錯誤現在會自動以退避機制重試。
- `CLAUDE_CODE_RETRY_WATCHDOG` now raises the default retry count for non-capacity transient errors to 300 and lifts the cap of 15 on `CLAUDE_CODE_MAX_RETRIES` — 預設重試次數提高到 300 次，並取消 15 次上限。
- `claude agents` session rows now show pull-request links as bare #N without the redundant "PR" label — 工作階段列表中的 PR 連結顯示更精簡。

**核心概念（簡單說）：**
這次 2.1.199 更新是一次以穩定性與可靠性為主的修補版本，重點修掉了大量跟「background agent / subagent」執行時的邊界情況錯誤有關的 bug（背景工作階段閃爍、閒置 agent 消失、daemon 自殺迴圈、SSH 冷啟動失敗等），同時強化了串流回應、rate-limit 重試、錯誤訊息呈現的健壯性，讓多 agent 並行工作時的體驗更穩定可預期。

**前端工程師實際應用：**
- **跟你工作的關聯：** 如果你有在用 Claude Code 的 background agent／subagent 功能做多工並行開發，這次修的多項 bug（例如 idle agent 消失、rate limit 429 自動重試）會直接影響你日常使用的穩定度。
- **具體場景：** 你同時開多個 background agent 平行處理不同任務（例如一個修 bug、一個寫測試），之前可能遇過閒置 agent 突然從面板消失、或工作階段在 Working/Idle 間閃爍的困擾，這次更新後應該會改善。
- **這週可以嘗試：** 更新到 2.1.199 後，測試看看疊加多個 slash-skill（如 `/skill-a /skill-b`）是否真的能一次載入全部 skill，並實際跑一次多個 background agent 並行的流程確認穩定性。
