**繁中改寫：**
Anthropic 推出「Anthropic Cyber Mission」，長期投入保護大家都依賴的系統，先從兩個方向開始：

- **關鍵基礎設施：** 推出 Critical Infrastructure Defense Program（CIDP），把前沿模型、駐點工程師與威脅研究帶給負責電網、水務、交通等 OT（operational technology）系統的資安服務商。
- **開源軟體：** 推出 OSS Scanner，免費用最強的模型定期幫開源專案做安全掃描。

OSS Scanner 是參考 Google OSS-Fuzz 的自願加入服務：每份報告包含 PoC（漏洞如何被利用）、說明，以及可行時的修補建議。報告由模型產生、不經人工審核，所以送達更快，但也可能有誤（例如嚴重度判斷錯誤），預期 true-positive 率超過 90%。

Anthropic 預測兩年後 AI 會讓「防守方」佔優勢——更容易在上線前抓到 bug、從頭寫出安全的軟體；但短期內不一定，因為利用漏洞的成本降低了，而驗證、揭露、修補仍然慢且依賴人力。

**核心概念（簡單說）：**
這篇的背景是「找漏洞變便宜了，但修漏洞沒有變快」。強模型能大量掃出開源專案的漏洞，但開源維護者大多是少數志工，收到一堆報告反而處理不完。所以 Anthropic 分兩條路：有能力大量處理的專案，直接加入 OSS Scanner 拿未審核的模型報告；沒能力的，繼續走人工驗證後的 CVD（coordinated vulnerability disclosure）流程。

可以把 OSS Scanner 想成「Dependabot 的進化版」：Dependabot 只告訴你「你用的某版本有已知 CVE」，OSS Scanner 是直接讀程式碼找出「還沒人知道的漏洞」，並附 PoC 與修補 patch。

**前端工程師實際應用：**
- **跟你工作的關聯：** 前端專案的 `node_modules` 動輒上千個開源套件，任何一個上游被掃出漏洞，最後都會變成你 `npm audit` 裡的警告；上游修得越快，你的升級壓力越小。
- **具體場景：** 如果你維護一個 npm 套件（例如公司開源的 React 元件庫或 Vite plugin），可以評估加入 OSS Scanner，讓模型定期掃描 XSS、prototype pollution、ReDoS 這類前端常見漏洞並附修補建議。
- **這週可以嘗試：** 在專案跑一次 `npm audit`（或 `pnpm audit`），挑一個 high 等級的警告，請 Claude Code 解釋漏洞成因、確認你的程式是否真的會走到那段 code path，再決定是升級還是用 `overrides` 處理。

## Claude Code · Changelog

**版本號 / 日期：** 2.1.295 / October 8, 2026

**變更項目：**
- Added `onFailure: "block"` for command and HTTP hooks: a hook that can't start, times out, or exits with an unexpected code blocks the action instead of letting it through — command / HTTP hook 新增 `onFailure: "block"`：hook 啟動失敗、逾時或回傳非預期 exit code 時，改為「擋下」動作，而不是放行。
- Added Program Status Protocol (OSC 7501) support: terminals that implement it can show whether Claude Code is working, waiting on you, or done — 支援 OSC 7501，有實作的終端機可以顯示 Claude Code 正在工作、等你回應或已完成。
- Added quoted text to the /copy picker, so a drafted message copies without its > markers — `/copy` 選單可以選引用文字，複製草稿時不會帶著 `>` 符號。
- Added `$.ui.notify` for mods; Added children to a mod's Button — mods 可以發原生通知，Button 也能放子元素（文字、chip）。
- Added `CLAUDE_CODE_RETRY_WATCHDOG_MAX_WAIT_MS` to limit how long unattended retry mode waits out 429 and 529 errors — 新環境變數，限制無人值守重試模式等待 429／529 的最長時間。
- [VSCode] Added a chat row for files Claude sends you: click a file's name to open it in the editor — VS Code 擴充中，Claude 傳給你的檔案會出現在對話列，點檔名即可在編輯器開啟。
- Changed MCP tool descriptions the model loads through tool search to be cut at 16,384 characters instead of 2,048 — 透過 tool search 載入的 MCP 工具描述上限從 2,048 字元放寬到 16,384。
- Changed subagents to preload at most 32 skills from the skills field, each once — subagent 最多預載 32 個 skill，每個只載一次。
- Changed WebSocket (ws) MCP servers: a message over 16 MiB is no longer parsed and closes the connection — WebSocket MCP server 單則訊息超過 16 MiB 會直接關閉連線。
- Improved Grep input handling: a search sent with grep's -l, -c or -r flag now runs instead of failing the call — Grep 工具收到 `-l`、`-c`、`-r` 參數時不再失敗。
- Fixed CSS, JavaScript and XML files returned by MCP tools being saved as .bin, which the Read tool refuses — 修正 MCP 工具回傳的 CSS／JS／XML 檔被存成 `.bin` 導致 Read 工具無法讀取。
- Fixed remote MCP servers in headless and SDK sessions staying disconnected after an outage longer than 15 seconds — 修正 headless／SDK session 中遠端 MCP server 斷線超過 15 秒就無法重連的問題，重連改為退避（最多 30 秒）。
- 另含 Claude apps gateway、Claude Tag、Cloud sessions 等多項變更，以及 13 項改善、97 項 bug 修正（詳見原始 changelog）。

**核心概念（簡單說）：**
這版最重要的是 hook 的 `onFailure: "block"`。過去 hook 若自己壞掉（腳本找不到、逾時、crash），Claude Code 預設是「放行」——也就是你寫來擋危險指令的安全 hook，只要一出錯就等於沒裝。`onFailure: "block"` 讓你把 hook 設成 fail-closed：hook 不能確認安全，就不執行。這是資安上「預設拒絕」的經典原則。

其他改動多半是 MCP 與 mods 生態的強化：MCP 工具描述上限放寬 8 倍，讓工具可以附更完整的使用說明；MCP 回傳的 CSS／JS 檔終於能被正確讀取；遠端 MCP 斷線後會自動退避重連，長時間跑的 headless 任務更穩定。

**前端工程師實際應用：**
- **跟你工作的關聯：** 很多前端團隊用 PreToolUse hook 擋掉 `rm -rf`、禁止直接改 `package-lock.json` 或在 commit 前強制跑 lint；這些守門 hook 現在可以設成「壞掉就擋」，不會默默失效。
- **具體場景：** 你在 `.claude/settings.json` 設了一個 PreToolUse command hook，呼叫 `scripts/guard.sh` 檢查 Bash 指令是否會動到 `dist/` 或 production 設定；加上 `onFailure: "block"` 後，就算有人把 script 改壞或 Node 版本不對導致 hook 跑不起來，危險指令也不會被放行。另外如果你用 Figma／瀏覽器類 MCP 取回 CSS 檔，現在 Claude 可以直接讀了。
- **這週可以嘗試：** 執行 `claude --version` 確認已更新到 2.1.295，打開專案的 hook 設定，把負責安全檢查的 hook 加上 `onFailure: "block"`，再故意把 script 路徑改錯測一次，確認動作確實被擋下。
