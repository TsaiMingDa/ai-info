最近在玩一個小小的個人專案：一個「AI 原生」的 macOS Dock，可以切換不同模式（寫作、開發等等），幫我保持專注。

我的 agent 可以自己調整每個模式的行為、也能新增模式；它用 jev 即時分類我正在做的事和收到的通知，然後依此採取行動。

這類 HCI（人機互動）的東西我想做很久了，只是以前要去碰 OS 底層實在太花時間。

暫時還不會公開，邊界情況還很多（不建議拿來用），但實驗起來很好玩！

**核心概念（簡單說）：**
傳統的 Dock 是一排「固定」的捷徑；Thariq 做的是一個會「看狀況」的 Dock：它持續觀察你現在開了哪些 app、收到什麼通知，用模型把這些事件分類（例如「這則 Slack 跟目前寫作無關 → 先壓下來」），再依當前模式決定要顯示、隱藏或延後什麼。更關鍵的是，模式本身的規則不是寫死的程式碼，而是讓 agent 依照你的口頭描述去改寫或新增——等於把「設定介面」換成「跟 agent 對話」。

他特別點出：以前做這種 OS 層級的 HCI 實驗，光是處理 macOS 的視窗、通知、accessibility API 就要花大量時間；現在 coding agent 把這段成本壓得很低，於是「個人化到只有自己會用的工具」變得值得做。這跟 Boris 前陣子提的「Mods 讓每個人自訂 Claude 長相與行為」是同一條思路：軟體從「大家用同一版」走向「每個人都有自己的變體」。

**前端工程師實際應用：**
- **跟你工作的關聯：** 前端工程師本來就擅長做 UI；當 agent 能幫你處理底層 API（Electron、Tauri、macOS accessibility、通知權限），你可以把自己的工作流程直接做成小工具，而不是只能忍受現成軟體的預設。
- **具體場景：** 用 Tauri + React 寫一個常駐 menubar 小工具，偵測你在 VS Code 時自動把 Slack 設為勿擾、切到瀏覽器 DevTools 時顯示目前的 Lighthouse 分數；分類規則用一段自然語言 prompt 交給 Claude 判斷，而不是寫一堆 if/else。
- **這週可以嘗試：** 列出一個你每天重複切換的「專注 / 溝通」情境，請 Claude Code 幫你用 `npm create tauri-app` 起一個最小原型，只做一件事（例如偵測前景 app 名稱並顯示在 menubar），先體驗 agent 處理 OS API 能省多少時間。

**原文：**
> feels like there needs to be a new way to distribute opensource software such that people can modify via agents but also get upstream automatically merged in
>
> coding agents can do this but they won't do it automatically
>
> （引用自己的貼文：experimenting with a lil personal project: an AI-native macOS dock with custom modes (writing, building, etc.) to help me stay focused …）

**繁中改寫：**
感覺需要一種新的開源軟體發佈方式：讓大家可以透過 agent 自由修改，同時又能自動合併上游（upstream）的更新。

coding agent 其實做得到這件事，只是它們不會自動去做。

**核心概念（簡單說）：**
這是接續上一則 Dock 專案的延伸思考。當每個人都用 agent 把開源工具改成「自己的版本」，就會出現經典的 fork 困境：你改得越多，跟上游的差異越大，之後要同步新版本時衝突越多，最後乾脆不更新、錯過安全修補。傳統解法是 plugin / config 系統（把可變的部分抽成擴充點），但那需要原作者事先設計好。

Thariq 的想法是：既然 agent 能讀懂你的修改「意圖」，那就該讓它定期自動 rebase——拉上游新版、理解你當初為什麼改、再把同樣的意圖套到新程式碼上，而不是逐行解 merge conflict。可以類比 Dependabot：Dependabot 自動幫你升級依賴；這裡則是要一個「能自動幫你重新套用客製化」的機制。目前缺的是讓這件事「自動發生」的發佈格式與流程。

**前端工程師實際應用：**
- **跟你工作的關聯：** 前端專案常 fork UI 套件（例如修改 shadcn/ui 元件、patch 某個 npm 套件），之後升級就很痛；這個概念直接對應你維護 fork 與 patch 的成本。
- **具體場景：** 你用 `patch-package` 修了一個 date picker 的 bug，套件升到新 major 後 patch 失效；與其手動重寫，可以把「當初為什麼改」寫成一份說明，交給 Claude Code 在新版上重新實作並跑測試驗證。
- **這週可以嘗試：** 盤點專案裡的 `patches/` 目錄或 fork 的元件，替每一個補上一段「修改意圖」註解（改了什麼、為什麼）；之後升級時就能直接把這段說明餵給 agent，讓它幫你重新套用。

> Early progress on accelerating drug development with Claude（Oct 27, 2026 · Science）
>
> （節錄）"Anthropic's life sciences team is working to accelerate curing disease."

**繁中改寫：**
Anthropic 的生命科學團隊公布了用 Claude 加速藥物研發的初步成果。過去幾個月，他們與六家藥物研發機構（BigHat Biosciences、Bristol Myers Squibb、Divergence Labs、Enveda、Generate Biomedicines、The Column Group）深度合作，也開始自己做藥物探索，包括兒童罕見型肌肉萎縮症的計畫，其中大部分科學與營運工作由 Claude 負責。

他們的策略是：藥物研發的瓶頸分散在整條流程裡，不只是「設計新分子」，還包括找標靶、量產優化、撰寫法規文件、設計臨床試驗等，所以要讓 AI 參與每一個環節。幾個案例重點：

- **Generate Biomedicines：** 科學家用 Claude Code 為 CAR T 細胞療法設計更短的基因片段，其中一版縮短約 70%，實驗中受體表現量約為原本 10 倍、殺腫瘤效率更好。
- **Divergence Labs：** 針對食物過敏，Claude 把研究目標轉成設計計畫，約一個月內幾乎自主產生約 35,000 個抗體設計，初步測試找到可結合與可剝離 IgE 的候選。
- **BigHat Biosciences：** Claude 連上實驗室資料系統提出分子改良，約 10 週測了約 1,010 個變體；過程中 Claude 與研究員還發現標準量測指標可能誤導，提出新指標並獲驗證。
- **Enveda：** 讓 Claude 審查製造文件，在 1,061 頁文件中抓到人類審查發現的全部 11 個問題，另外多抓到 7 個，審查時間減少 89%；一份法規文件初稿從約三個月縮短到四小時。
- **The Column Group：** 成立新公司 Pleiades，用 Claude 讓小團隊跑更多、更複雜的藥物計畫。
- **Bristol Myers Squibb：** 用 Claude 評估早期臨床試驗計畫與成功機率，預計 2027 年擴大合作。

**核心概念（簡單說）：**
這篇的重點不是「AI 設計出神藥」，而是 Claude 被當成跨流程的 agent 嵌進真實工作：接上實驗室資料系統、讀取上千頁文件、產出設計並交給自動化實驗室驗證，再根據結果迭代。這跟軟體開發的 agentic loop 是同一個模式——「提出改動 → 跑測試 → 讀結果 → 修正」，只是測試環境換成濕實驗室。

特別值得注意的是 BigHat 案例：Claude 不只是照指標優化，還懷疑「指標本身有問題」並提出新的量測方法。這對應到軟體世界，就像 agent 不只修測試，還指出「這個測試其實沒在測你以為的東西」。Enveda 的案例則說明，大量的價值其實藏在文件審查、法規撰寫這類「不性感」的工作裡。

**前端工程師實際應用：**
- **跟你工作的關聯：** 這篇示範了 agent 接上「領域工具 + 驗證回饋」後的威力；前端也一樣，agent 接上瀏覽器、測試、視覺比對後，才能真正自主迭代，而不是只吐程式碼。
- **具體場景：** 讓 Claude Code 透過 chrome-devtools MCP 打開頁面、跑 Lighthouse、讀 Core Web Vitals，再修改程式碼並重測——這就是 BigHat「提出變體 → 實驗室測 → 回饋」流程的前端版本。
- **這週可以嘗試：** 挑一個你懷疑「指標可能誤導」的地方（例如 coverage 很高但常出 bug 的元件、或 Lighthouse 分數高但使用者覺得卡的頁面），請 Claude 分析原始數據並提出更貼近實際體驗的指標，練習讓 agent 質疑量測方式本身。

## Claude Code · Changelog

**版本號 / 日期：** 2.1.312 / October 27, 2026

**變更項目：**
- Added `oidc.user_id_claim` to the Claude apps gateway, to identify people by an id_token claim other than `sub`, such as Microsoft Entra ID's `oid` — Claude apps gateway 新增 `oidc.user_id_claim`，可用 `sub` 以外的 id_token claim（例如 Entra ID 的 `oid`）識別使用者。
- Added click to send: in fullscreen, clicking the "to send now" hint under a queued message sends it right away — fullscreen 模式下，點擊排隊訊息下方的「to send now」提示即可立刻送出。
- [Cloud sessions] Added an effort level to the model picker when you create or edit a routine that runs in the cloud — 建立或編輯雲端 routine 時，model picker 可以設定 effort level。
- [Cloud sessions] Added a Bash editor with colors, line numbers and a Copy button to the setup script box — 雲端環境的 setup script 改成有語法上色、行號與複製按鈕的 Bash 編輯器。
- Changed Bedrock, Vertex, Foundry and Mantle to use the shorter system prompt for model names Claude Code doesn't recognize; set `CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT=0` to keep the full prompt — 在雲端供應商上使用無法辨識的自訂模型名稱時，改用精簡版 system prompt，可用環境變數保留完整版。
- Changed automatic model switches after a flagged message to also cover unrecognized model names; set `CLAUDE_CODE_DISABLE_REFUSAL_FALLBACK=1` to turn them off — 訊息被標記後的自動切換模型機制，現在也涵蓋自訂模型名稱，可用環境變數關閉。
- Changed usage limit messages to call the 5-hour window the "5-hour limit" instead of the "session limit" — 用量上限訊息改稱「5-hour limit」，不再叫「session limit」。
- Changed prompt and agent hooks to run at most 24 at a time per session (sub-agents included), plus at most 12 that have waited longer than their timeout; a timeout under 1 second now counts as 1 second — prompt / agent hooks 每個 session 同時最多跑 24 個（含 sub-agent），逾時等待的最多 12 個；低於 1 秒的 timeout 一律視為 1 秒。
- Changed a subagent's `autoCompactWindow` to lower the window set by `CLAUDE_CODE_AUTO_COMPACT_WINDOW` — subagent 的 `autoCompactWindow` 現在可以調低全域設定的壓縮視窗（但不會調高）。
- Changed Claude Code to stop sending the `claude_code.safety_event` OpenTelemetry event — 不再送出 `claude_code.safety_event` OpenTelemetry 事件。
- [VSCode] Changed usage limit resets to show a clock time ("Resets at 3:10 PM") — VS Code 擴充改為顯示實際重置時間。
- Improved the prompt's effort indicator: a change made mid-task now says it may wait for your next message — 任務進行中調整 effort 時，指示器會說明可能要到下一則訊息才生效。
- Improved WebFetch errors in cloud sessions: an unresolvable host is explained as possibly outside the allowed network domains — 雲端 session 中 WebFetch 解析不到 host 時，會提示可能是不在允許的網域清單內，並點名要放行的 host。
- [Claude Tag] Improved the retry notice in Slack to name the model in use, or say rate limits were hit — Slack 裡的重試通知會寫出使用中的模型或說明碰到 rate limit。
- 另有 22 項 bug fixes（頁面預設收合，未逐條列出）。

**核心概念（簡單說）：**
這版主要是「雲端 session 與企業部署」的打磨：雲端 routine 可以設 effort、setup script 編輯體驗變好、WebFetch 被網路白名單擋時錯誤訊息更好懂；企業端則可用 Entra ID 的 `oid` 識別使用者，自訂模型名稱在 Bedrock / Vertex 等平台上的行為也更一致。另一個值得注意的是 hooks 併發上限——如果你寫了很多 prompt / agent hooks，現在有明確的同時執行上限（24 個），避免 hooks 把 session 卡死。

**前端工程師實際應用：**
- **跟你工作的關聯：** 若你用雲端 routine 跑每日任務（例如自動更新依賴、產生報告），現在可以針對任務難度調 effort，簡單任務用低 effort 省用量；WebFetch 錯誤也更容易判斷是不是網路白名單沒設。
- **具體場景：** 你在雲端環境設了一個每晚跑 `npm outdated` + 自動開 PR 的 routine，setup script 要裝 `pnpm` 與 Playwright 瀏覽器；新的 Bash 編輯器讓你直接檢查腳本行號與語法，並把 effort 設為 low，降低每天的用量消耗。
- **這週可以嘗試：** 執行 `claude --version` 確認升到 2.1.312；如果你有自訂 hooks，檢查有沒有 timeout 設成小於 1 秒的（現在會被當成 1 秒），順便評估是否有 hooks 數量多到可能撞到 24 個併發上限。
